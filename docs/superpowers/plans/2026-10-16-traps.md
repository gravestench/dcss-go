# Source-backed Traps Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Checkboxes track completion; make one implementation commit for the whole trap category, as requested by the user.

**Goal:** Make every active pinned-source trap an executable Lua-defined game feature with saved ECS state.

**Architecture:** Per-trap Lua definitions and effect files own game rules. A generic Akara trap entity owns mutable trap state while the grid owns underlying terrain. Lua placement, movement, rendering, and validation use the existing mod/runtime interfaces; Go gains only reusable context primitives if necessary.

**Tech Stack:** Go, Akara, gopher-lua, embedded layered mod files, Go JSON saves, `_test.lua` fixtures.

**Spec:** `docs/superpowers/specs/2026-10-16-traps-design.md`

## Global Constraints

- Target pinned DCSS source `e60ba3568b0c26447ad36ec5c7b963eb04b2778f` and its ten active trap IDs.
- Keep every game-specific rule in embedded Lua files; no inline Lua or Go trap-ID switch.
- Keep generated source data committed; normal builds never read C++.
- Use saved Akara components for mutable trap state and dense grids for terrain.
- Keep handwritten Go/Lua lines at or below 120 columns and prefer 80.
- One contiguous trap implementation commit; merge verified work into local `main`.

## Review Focus

1. A trap and floor item share a cell: activating/removing the trap preserves the item.
2. A teleport lands on another trap: activation follows the source's recursion rule and never loops indefinitely.
3. A mod adds a trap ID: discovery and save validation accept it only with a complete definition and effect.
4. A saved one-shot trap was already consumed: restore never restores its charge or rerolls its effect.
5. A removed version-34 trap appears in a vault: the source location gets an explicit error or source-defined inert behavior.
