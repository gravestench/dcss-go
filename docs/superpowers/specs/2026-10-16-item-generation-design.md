# Source-backed item generation

## Intent and scope

Every item generated by a vault, acquirement scroll, or later floor-loot
system should use the same source-backed rules. A mod author should be able
to add a subtype in one item content file, including its generation metadata,
without editing a Go switch or several lists. Generated items must retain
their exact rolled state through save and restore. The rules should remain
readable as focused Lua modules rather than one translation of
`makeitem.cc`'s class switch.

This slice covers source class and subtype selection, per-run item sets,
quantities, charges, enchantment, brands and egos, manuals, random books,
random artefacts, unrandom artefacts, and generation eligibility for every
active base item class. It replaces the provisional random-vault-item and
acquirement pickers. Vault item specifications continue to own their syntax;
item generation receives a typed request after that syntax is resolved.
Inventory commands, ordinary item use, and equipment rules remain in their
existing domains. Generated artefact properties must be represented and
consumed by existing mechanics that already handle those properties. Effects
whose mechanics have not yet been ported stay explicit, saved pending
properties for the corresponding later domain; they are never silently
discarded or given an invented substitute.

and generation-related `art-func.h` hooks for unique definitions, and
`dungeon.cc`, `mapdef.cc`, and `acquire.cc` for caller semantics. Refresh
tools may read these sources deliberately; normal builds and play use
committed Lua content only.

## Lua ownership and extension contract

`policy/item_generation` owns one public request and result contract. A
request can specify a class or fixed kind, source depth, source quality,
whether uniques are allowed, purpose, and explicit overrides such as
quantity or ego. Quality distinguishes ordinary, `*` depth boost, good, and
superb instead of reducing them to a generic bonus. The generator resolves
class first, then subtype, then instance properties in source order. It
returns the complete rolled item state. A shared materializer attaches that
state to an ECS entity at a caller-selected location. Rolling for a menu and
placing an item later must never reroll it.

Each source-generated class has a small Lua policy module registered through
the existing layered mod loader. The class policy owns source algorithms;
individual item content files own subtype metadata and named exceptions that
belong to that subtype. A mod-added subtype in an existing class is discovered
with its content file. A mod can replace a class policy at the same relative
path through the layered VFS. Stable item, class, brand, and property IDs
come from shared `ids` or `constants` modules and are imported where used.
Source provenance is a nearby comment, not a runtime field in a declaration.

The ordinary random-class weights, depth-dependent miscellaneous and early
wand adjustments, and superb-class weights follow `makeitem.cc` and
`dungeon.cc`. Each class then follows its source eligibility and subtype
distribution. Named or forced kinds skip only the relevant selection roll;
they still receive source instance rolls and valid explicit overrides.
Classes that DCSS only creates through a forced path, such as runes, the
Orb, and corpses, do not enter an ambient random pool. Removed, enum-only,
legacy, and `nogen` definitions remain inspectable but cannot enter a pool
that the source excludes them from. No class falls back to a uniform draw
over all catalog entries.

The currently committed base catalog contains 368 definitions across 16
classes, including 44 explicitly removed entries. Those figures are audit
checks, not a substitute for source eligibility rules. Missing generation
metadata is added to the committed per-item Lua definitions by deliberate
source-backed import tools. Import output is reviewed and committed; Go
builds do not regenerate it.

## Per-run choices and artefacts

The source chooses one subtype from each of four item sets at game start:
hex, beam, and blast wands, and concealment scrolls. A Lua-defined session
component on the player stores the four choices. Generation and scroll
eligibility use those saved choices; restore does not redraw them. A separate
saved component on the player records unique-artefact generation history,
including the source distinction between ordinary generation and nonlevel
generation needed for fallback randarts.

All 127 entries in `art-data.txt` are imported as individually named,
committed Lua definitions with their source order, base type, properties,
flags, and fallback information. This includes `nogen` entries and the dummy
placeholder as nonrandom definitions. The source's random eligibility,
duplicate handling, and randart fallback rules determine which can appear.
Random artefact property types, weights, value rolls, compatibility checks,
rerolls, and names follow `artefact.cc`. Generation-affecting unique hooks
from `art-func.h` become focused Lua handlers; unrelated on-use and combat
hooks remain with their later domains. The item entity retains an explicit
Lua-defined artefact component with kind, identity or seed, name, appearance,
property values, and property knowledge. Manuals and random books likewise
retain their rolled skill, points, or spell list in dedicated components.

The existing `core.item` remains the ordinary identity, quantity, plus,
charges, and ego record. Rich instance state belongs in Lua-defined
components, so a new modded property does not require a Go item struct field.
Presentation and identification read these components. Current equipment,
combat, and status consumers use applicable artefact properties; properties
for unported effects remain named and saved for their later full-domain
implementation.

## Callers and save lifecycle

Vaults call the shared generator after resolving their selected expression.
The vault-origin component and selected source record stay attached to the
resulting ECS item. Explicit quantity, depth, and quality modifiers are
applied in the source order. Gold, corpse, and skeleton source paths retain
their distinct placement rules. Existing monster gear and starting gear
remain fixed source-defined loadouts where the source fixes them, but any
random item request they make uses the same generator.

Acquirement rolls all offered items before displaying its menu. It uses the
source class shuffle and item selection policy, then saves each complete
offered item as an ECS entity in a generic reserved location owned by the
scroll. A reserved item is neither floor loot nor carried equipment. The
kernel's item role permits exactly one of position, carrier, or reservation;
restore validates a live reservation owner and its menu reference. Cancel
and save/restore retain the same entities and menu labels. Choosing one
moves that entity to the player's floor cell and disposes of the remaining
offers according to source unique-item history rules. It does not generate
a new item at grant time.

Session item-set choices and unique history, item instance components,
reservations, and acquirement menu references are included in the Go save
format. Restore validates catalogue IDs, component schemas, reserved-item
ownership, artefact identity and property compatibility, and duplicate
unique artefacts before play resumes. The ruleset hash governs changes to
committed Lua content. C++ save compatibility and bit-for-bit C++ RNG
sequence compatibility are outside this port; identical Go seed, ruleset,
and actions must reproduce identical outcomes.

## Failure behavior

At mod load, validate every generation-eligible definition and class policy:
positive weights, named IDs, valid property types, compatible brands, and
nonempty eligible pools. A definition may explicitly declare that it is
forced-only or not generated. An unknown or incomplete generation rule
fails with its effective mod path and item ID. During generation, an
impossible forced request or exhausted unique pool fails with the caller's
vault or scroll context. No request silently falls back to a different
subtype or to uniform catalogue selection. Source-defined no-spawn and
fallback outcomes remain explicit.

## Verification

Production schemas, catalogues, constants, and policy modules are imported
by `_test.lua` tests; tests never redeclare their own item definitions.
Deterministic draw-boundary tests cover every active class and each source
quality mode, fixed subtype requests, item-set exclusions, quantities,
charges, brand eligibility, armour and weapon plusses, manuals, books,
randart property compatibility, unique-artefact eligibility, and fallback.
Tests check source weight tables and imported unique-definition counts,
including `nogen` and dummy entries. Layered-mod tests add one item file and
replace one class policy without editing the base registry, then reject
malformed or incomplete metadata with a source-addressed error.

Integrated Go tests cover vault random items and fixed items, acquirement
offer generation, cancellation, selection, save/restore, reserved-item
validation, unique history, and display/identification of rolled artefacts.
They prove that restoring or reopening a menu does not reroll an offer and
that a reserved item cannot appear in floor or inventory queries. Item
generation uses persisted named RNG streams. At the category boundary, run
the relevant Lua and Go suites, importer consistency checks, Go build and
vet, and Go/Lua style checks. Commit the contiguous item-generation domain
as one implementation commit after verification.
