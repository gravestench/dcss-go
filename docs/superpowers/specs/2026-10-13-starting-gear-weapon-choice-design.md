# DCrawl Go: starting gear and weapon choice

Date: 2026-10-13

## Purpose and boundary

This slice gives the existing Human/Fighter Dungeon scenario a source-backed starting inventory and an explicit starting-weapon choice. It also imports and resolves the guaranteed equipment vocabulary for all 25 selectable tag-34 jobs, so later character starts reuse the same catalog. Human/Fighter remains the only playable species/job pair in this slice. The player sees the weapon choice before the first turn, then enters the same fixed two-floor Dungeon. Imported gear for other jobs is content coverage, not a claim that those starts are playable.

The design follows the port-wide content rule: optional developer importers generate reviewable artifacts committed to the Go repository. Ordinary builds, tests, CI, saves, and gameplay use only committed content and never require the C++ checkout. Dynamic items remain ECS entities, terrain remains a dense grid, and the ASCII client uses Bubble Tea/Lip Gloss. The paused C++ refactor is untouched.

## Pinned source behavior

The source of truth is `/Users/dylanknuth/src/crawl/crawl-ref/source` at Git revision `e60ba3568b0c26447ad36ec5c7b963eb04b2778f`, `TAG_MAJOR_VERSION=34`. The already committed `jobs.json` contains all 31 jobs, 25 selectable jobs, and their ordered raw equipment strings. Those 25 jobs contain 36 distinct equipment strings. `jobs.cc:give_job_equipment` parses them as item specs and calls `newgame_make_item` in list order. The pinned strings use only item name, `q:`, `plus:`, `charges:`, `ego:`, and `no_exclude`; parsing must reject any other syntax rather than silently ignore it. The source parser's general vault syntax is outside this slice. Preserve the original string for traceability, and commit a typed resolved grant with stable item kind ID, quantity, enchantment or charges, ego, and `no_exclude` metadata. The `no_exclude` tag is retained even though item-set exclusion behavior is not yet ported.

`newgame.cc:_get_weapons` starts from short sword, mace, hand axe, spear, falchion, quarterstaff, and unarmed. A job with `WCHOICE_GOOD` upgrades short sword→rapier, mace→flail, hand axe→war axe, spear→trident except for a small Fighter, and falchion→long sword. `ng-restr.cc:weapon_restriction` bans grasped weapons for no-grasping species and normally bans quarterstaff except for Gladiator or quadrumanous Fighter. Recommendations use the species' recommended weapon **skills**, with Fighter's short blades deliberately not recommended. These are pure `character` rules over `content.Catalog`, independent of the terminal. For Human/Fighter, the six legal choices are rapier, flail, war axe, trident, long sword, and unarmed; quarterstaff is banned. Unarmed creates no weapon item. The menu shows legal options and recommendation status, and the selected stable weapon ID is validated again when the game is created.

`ng-setup.cc` creates the chosen Fighter weapon first, then Fighter's scale mail, buckler, and potion of might. The usable weapon, body armour, and shield are equipped when their slots are empty; the potion stays carried. Human has no innate restriction that changes these grants. The current potion of curing on the floor remains a fixed scenario item. `_give_bonus_items` is Sprint-only and must not be added to this normal Dungeon start. In the current Go scenario, HP 20, player base damage 4, and rat combat remain controlled fixture values; the equipped weapon does not yet alter attacks.

## Approaches considered

1. **Focused starting catalog (selected).** Import every item kind referenced by the 25 jobs' guaranteed equipment, every weapon candidate/upgrade needed for their choice rules, and the existing floor-potion fixture. Resolve specs into committed typed grants. This keeps all starter data auditable while allowing one playable start to be implemented and verified now.
2. Import every active item subtype and every item behavior at once. That would couple starting gear to identification, generation, brands, effects, combat, and equipment restrictions before those domains exist. It makes this slice too large to review as one coherent step.
3. Hand-code only Human/Fighter's four objects. That is shorter initially but duplicates the later import and bypasses the agreed source-traced content path. It does not give later jobs a reusable starting-gear catalog.

## Ownership and data flow

`content` owns immutable item-kind definitions and ordered `StartingGrant` lists per job. An item kind has a stable subtype ID, object class, display name, glyph, stackability, permissible equipment slot, and a weapon skill where relevant. The starting-gear artifact records schema version, pinned revision/tag, sorted source-file SHA-256 hashes, the kind records, and resolved job grants. It covers all 36 distinct pinned raw specs, all active choice candidates and upgrades, and `POT_CURING`. Import validation rejects missing/duplicate IDs, names that resolve ambiguously, unknown object classes, inactive tag-34 IDs, unsupported tags, invalid quantities/charges, bad ego values, missing job coverage, and provenance mismatch with committed species/jobs. Runtime load returns defensive copies and cross-checks job IDs and original spec strings against `jobs.json`. There is no mutable package-level item registry.

The optional `cmd/importstartinggear` reads only the pinned C++ source and committed job content needed to validate the source revision. It writes the artifact atomically and has a read-only `-check` mode. Its parser is deliberately limited to the pinned initializer, enum, and item-name forms; any newly encountered upstream syntax requires an explicit importer change. Normal `go build` and `go test` do not invoke it. The source trace includes `job-data.h`, item enum/name/property sources needed to resolve each kind, and the weapon-choice rule anchors. If source names are indirect, a small explicit name-to-ID table is allowed in the importer only when every entry is checked against a live enum and recorded with a source anchor; runtime never contains such a translation table.

`character` computes ordered weapon options and their three-way restriction status from species, job, weapon skill, size, and mutations. It does not create items or mutate ECS. The terminal owns a pregame weapon-selection state for Human/Fighter; movement and turns are unavailable until selection. The menu accepts a legal option, quit, or load of an existing version-3 save. Loading a save bypasses new weapon selection. The terminal passes the chosen stable weapon ID to `game.NewScenario`, which revalidates it and records that choice on the player, including `WPN_UNARMED`. The game then creates carried item entities in source order. A separate `Equipped` component on item entities records the slot; each slot has at most one item. The existing `CarriedBy` component remains the authoritative owner of inventory items. Item state stores quantity, enchantment, charges, and ego without overloading one numeric field for unrelated concepts. The game view exposes carried and equipped item names; the terminal lists them clearly.

Save version 3 records the selected weapon ID on the player and persists item entities with their properties/equipment slots. Restore builds a separate game and rejects missing or duplicate equipped slots, equipment without a player carrier, impossible quantities/properties, a selected weapon inconsistent with the equipped weapon (or with unarmed), and invalid item-kind references before replacing the live game. A valid saved run retains the current deterministic continuation. Version-2 saves are rejected by the version check; no compatibility shim is added.

## Errors, tests, and remaining work

Importer errors name the source file, job, raw spec, and field where possible. Generation failure or stale `-check` leaves the committed artifact unchanged. Terminal start errors remain visible without constructing a partial game; failed loads leave the running game unchanged. No command consumes a Dungeon turn while selecting a weapon.

Acceptance checks:

1. The generated artifact resolves all 36 distinct starting specs for all 25 selectable jobs, preserves grant order and raw strings, and has pinned revision, tag, and source hashes. Two explicit generations are byte-identical; `-check` passes against the committed file and fails on stale bytes without changing it. A Go-only copy builds and tests with no C++ checkout.
2. Pure choice tests cover good-weapon upgrades, small Fighter spear exception, no-grasping, quarterstaff exceptions, recommendation direction, unknown IDs, and the six Human/Fighter options. The menu can select each legal option, reject an invalid input without advancing time, quit, and load a version-3 save.
3. An armed Human/Fighter starts with one selected weapon, scale mail, buckler, and potion of might carried; the first three occupy valid unique slots and the potion is not equipped. Unarmed has the three job grants but no weapon entity. The floor potion remains on the map. Neither creation nor menu navigation advances auts.
4. Save/restore preserves the full loadout and seeded continuation. Corrupt versions, duplicate equipment slots, misplaced equipment, impossible item state, and unknown item IDs fail without changing the live game.
5. `go test ./...`, `go vet ./...`, both existing content artifact checks and the new explicit check pass. A terminal startup demonstrates weapon selection and the equipped inventory.

This slice does **not** apply item effects, item identification, ranged ammunition rules, species-specific armour substitutions or usability filtering, weapon-derived combat damage, starting skill reassessment, other jobs as playable starts, Sprint extras, or full character creation. Those require their own content and gameplay slices. The inventory must distinguish imported starting gear from working effects and update save status to version 3.
