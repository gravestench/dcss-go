# DCSS console presentation and flow parity

## Intent and boundary

Make `go run ./cmd/dcrawl` look and operate like the pinned DCSS console client for the Go port's current playable domain. A player should recognize the original startup, character creation, dungeon screen, inventory, skills screen, messages, prompts, colors, and keys at first launch. Human/Fighter and the fixed two-floor Dungeon remain the only playable character and world. Menus and commands for unported features remain visible and give a clear, free, in-client unavailable response when selected.

Two deliberate differences from the C++ console are approved: the dungeon viewport grows to use space beyond the original layout on large terminals, and unsupported gameplay reports its absence instead of pretending to work. The minimum terminal is 79 columns by 24 rows, matching `source/defines.h`. This slice does not port new combat, generation, training, item effects, or C++ saves.

Reference is `/Users/dylanknuth/src/crawl/crawl-ref/source` at `e60ba3568b0c26447ad36ec5c7b963eb04b2778f`. Its source files define behavior; a local console binary was used to cross-check the 79×24 startup, species, background, weapon, name, play, inventory, and skills screens. The binary's compiled version string differs from the pinned commit, so its captures are visual evidence only when the corresponding source agrees.

## Screens and transitions

The Bubble Tea application owns one explicit screen state: startup, species, background, weapon, name, play, inventory, skills, help, confirmation, or unavailable notice. It owns focus, menu descriptions, notices, terminal size, and the current `game.Game`. Rendering and menu navigation never advance game time. Each screen fills a canvas of exactly the terminal's width and height, even when the original menu content occupies only the upper left.

Startup follows `source/startup.cc:413-540,565-925`: the welcome banner, name input, game-mode choices and descriptions, and a saved-game entry when the configured Go save is present. Dungeon Crawl enters character creation. A valid Go save loads from the startup entry. Other modes and unavailable startup facilities retain the source labels and show an unavailable explanation. A failed load stays on startup with its error and leaves any live game untouched.

Character creation follows `source/newgame.cc:309-340,1065-1415,1690-1790,2001-2029` and `source/species-groups.h`. Species appears in Simple, Intermediate, and Advanced columns with original letter assignments; backgrounds appear in the original grouped columns and letter order. Focus changes the description line. The player may choose species or background first and return with the source navigation keys. All source-visible options are shown. Existing committed species and job catalogs supply names, legal pair information, and recommendations; a new committed presentation-content artifact supplies source-ordered menu groups and the description text from `source/dat/descript/species.txt` and `source/dat/descript/backgrounds.txt`. Only Human/Fighter proceeds to weapon selection; another choice explains that its start is not yet ported and keeps the player in the menu. Unsupported random and aptitude subcommands use the same unavailable response; `?` opens the local help page.

The Human/Fighter weapon screen uses `a`–`f`, source order, weapon names, aptitude annotation, recommendation color, and return/help controls from `source/newgame.cc:1690-1790`. Selecting a legal weapon creates the existing scenario after a valid name is known. If the startup name was blank, show the source-style post-weapon name prompt before creating the run. Name input follows `source/ng-input.cc:62-95` and its 30-column limit from `source/externs.h`; invalid or cancelled names do not create a game. The name appears in the HUD and persists through Go save and load. The player name belongs to the player entity; adding an optional name to the existing version-4 Go snapshot keeps existing version-4 saves loadable. An old snapshot with no name displays `Adventurer` until the player starts a new named run.

During play, `Esc` closes a modal page or cancels a prompt. Inventory (`i`) uses the source's full-screen grouped listing rather than a box appended below the map (`source/invent.cc:1269`). Skills (`m`) uses the source's columns and footer (`source/cmd-keys.h`, `source/skills.cc`), showing the player's committed starting levels and the imported Human aptitudes. Training percentages, cross-training, and other unported values show a restrained unavailable marker; selecting those controls explains the limitation without changing time. Help (`?`) lists source keys and identifies which commands work. Player death displays the source-style death message and a terminal state from which the player can return to startup; unported score and morgue actions are identified as unavailable. No screen renders the existing `DCrawl · Dungeon slice` banner or custom shortcut footer.

## Dungeon composition

A small `Canvas` owns a row-major grid of glyph, foreground, background, and emphasis. `Layout` allocates dungeon, gutter, 42-column HUD, nearby-monster list, and bottom messages. These are separate, testable responsibilities; the terminal model supplies a read-only presentation snapshot, and the canvas renders it. Lip Gloss emits styles; Bubble Tea owns the alternate screen, input, and resize events. No C++ renderer or content importer runs in normal Go builds.

At 79×24, use the default source inline geometry from `source/viewgeom.cc`: 33×17 dungeon viewport, four-column gutter, 42-column HUD, four-line monster area below the 13-line HUD, and seven-line message area across the bottom. Keep source HUD field positions, labels, bar shapes, status colors, and message alignment from `source/output.cc:291-478,1294-1508` and the default 16-color choices in `source/initfile.cc`. Real HP, MP, Str, Int, Dex, equipped weapon, Dungeon depth, and elapsed aut come from `game.View`; the current Fighter's starting `Shield-Bearer` title is source-backed by `source/skills.cc:91`. Unported AC, EV, SH, XP, noise, and quiver use visible placeholders at their original positions rather than invented gameplay values. Nearby actors and items use source-like glyphs and colors where current view data supports them. The viewport centers on the player, draws known terrain and entities, and fills cells outside the current small level with unexplored blank space.

Above 79×24, preserve the HUD width, gutter, and pane order while expanding the dungeon viewport into additional columns and rows; the message and nearby-monster areas fill the remaining height. No terminal column or row is left unused merely because the original DCSS viewport cap was reached. The source's original large-terminal behavior was observed to leave substantial blank space; this expansion is the requested difference. On a resize below 79×24, show the source-style resize warning across the available screen and preserve current menu focus/game state. Restoring a valid size redraws the same state without advancing a turn.

## Keys, prompts, and effects

Use source bindings from `source/cmd-keys.h` for the supported domain: eight-way `h/j/k/l/y/u/b/n` and arrow movement where available, `.` or `s` wait, `g` or `,` pickup, `<` and `>` stairs, `i` inventory, `m` skills, and `?` help. Keep menu letters and `Esc` behavior local to each screen. For visible but unported commands, show an explanatory message and spend no aut. In particular, `q` is quaff and `L` is run right; neither silently quits or loads. The existing Go-only `c` skills and in-play `L` load shortcuts end. Normal `S` asks the source-style save-and-exit confirmation, writes the configured Go save, and exits only after a successful write; Ctrl-S saves and exits without the query. Ctrl-Q asks for abandonment confirmation. Cancelling any confirmation is free. These source semantics come from `source/main.cc:2353-2385` and `source/cmd-keys.h`.

The UI never dispatches an unsupported command to a game system. Supported commands still pass through `game.Step` exactly once. Modal rendering, key navigation, errors, and resize are pure with respect to game time. A `WindowSizeMsg` redraw may alter only UI layout.

## Data and ownership changes

Keep terminal-only coordinates, color names, and key bindings in the terminal package with explicit source anchors. Source menu grouping and description prose are content: generate them into a reviewable artifact committed in `internal/content/generated`, with the pinned source revision and file hashes. An importer runs only for intentional upstream refreshes. Gameplay content otherwise comes from existing committed Go catalogs; no C++ checkout is required at runtime. Add only read-only `game.View` fields needed to distinguish nearby actor names, item classes, the player's display name, and equipped item labels. The player name is state on `ecs.PlayerControlled` and is round-tripped by the Go snapshot. Presentation code does not reach into ECS stores, mutate game state, or calculate unported combat stats.

The current `StartModel`, `Model`, and `Render` may be replaced rather than wrapped in a compatibility layer. Separate the screen controller, source-specific menu data, layout geometry, cell drawing, and `game.View` adaptation into focused files so future domains can fill the existing placeholders without rewriting screen flow.
